# Разбор кода JvmComprehension с точки зрения JVM

## Подготовительный этап — загрузка классов (до старта `main`)

Ещё до выполнения первой строки JVM должна загрузить и подготовить классы, которые встречаются в коде:

- **Bootstrap ClassLoader** загружает базовые классы из `java.lang`: `Object`, `Integer`, `String`, `System`.
- **Platform/Application (System) ClassLoader** загружает наш класс `JvmComprehension` (он лежит в classpath приложения).
- Для каждого загруженного класса в **Метаспейсе (Metaspace)** создаётся структура `Class` — метаданные: сигнатуры методов, константный пул, ссылки на суперклассы, статические поля и т.д. Метаспейс — это память вне кучи (off-heap, в native memory), в Java 8+ заменившая PermGen.
- JVM находит метод `main`, создаёт для потока `main` **стек потока (Thread Stack)** и кладёт на него первый **фрейм стека (stack frame)** — для метода `main()`.

## Построчный разбор

### `int i = 1;` — строка 1
`i` — примитив `int`. Он хранится **прямо во фрейме стека** метода `main`, в так называемой таблице локальных переменных (local variable table). Никакого объекта в куче не создаётся — примитивы не «оборачиваются». JVM просто кладёт байты значения `1` в отведённую ячейку фрейма.

### `Object o = new Object();` — строка 2
- Оператор `new` обращается к JVM с просьбой выделить память под объект типа `Object`.
- JVM выделяет память в **куче (Heap)**, точнее — обычно в **Young Generation → Eden**, поскольку почти все новые объекты создаются именно там (гипотеза поколений: «большинство объектов умирают молодыми»).
- В заголовке объекта (object header) записывается ссылка на метаданные класса `Object` в Метаспейсе (mark word + указатель на class-метаданные).
- Вызывается конструктор `Object()`.
- Переменная `o` во фрейме стека `main` хранит не сам объект, а **ссылку (reference)** — адрес объекта в куче.

### `Integer ii = 2;` — строка 3
- Здесь срабатывает **автобоксинг** (`Integer.valueOf(2)`), так как `2` — это `int`-литерал, а переменная объявлена как объект `Integer`.
- `Integer.valueOf()` использует **кэш `Integer` (Integer Cache)** для значений от -128 до 127 — значение `2` попадает в диапазон, поэтому JVM **не создаёт новый объект в куче**, а возвращает уже существующий закэшированный объект `Integer` (эти объекты созданы один раз при инициализации класса `Integer` и живут в куче постоянно, пока не выгружен classloader).
- `ii` во фрейме стека `main` хранит ссылку на этот кэшированный объект.

### `printAll(o, i, ii);` — строка 4
- JVM создаёт **новый фрейм стека** для вызова `printAll` и кладёт его поверх фрейма `main` (стек растёт вызовами методов, LIFO).
- В новый фрейм копируются:
    - параметр `o` — копия ссылки (сам объект `Object` в куче не копируется, копируется только адрес);
    - параметр `i` — копия примитивного значения `1`;
    - параметр `ii` — копия ссылки на кэшированный объект `Integer`.
- Управление передаётся в метод `printAll`, счётчик команд (PC register) потока переключается на байткод этого метода.

### `Integer uselessVar = 700;` — строка 5
- Снова автобоксинг, но `700` **выходит за пределы диапазона кэша** (-128…127), поэтому JVM **создаёт новый объект `Integer`** в куче (в Eden).
- Ссылка на этот новый объект кладётся в локальную переменную `uselessVar` в фрейме `printAll`.
- Этот объект — хороший кандидат на скорую сборку мусора: он не используется нигде дальше и не возвращается наружу.

### `System.out.println(o.toString() + i + ii);` — строка 6
- `o.toString()` — виртуальный вызов метода. JVM ищет метод `toString()` через таблицу виртуальных методов (vtable) объекта, на который ссылается `o` (динамическая диспетчеризация). Так как реальный тип объекта — `Object`, вызывается `Object.toString()`, который возвращает строку вида `java.lang.Object@<hashcode>`.
- Компилятор превращает конкатенацию строк (`+`) в использование `StringBuilder` (`new StringBuilder().append(...).append(...)...`) — создаётся ещё один временный объект в куче (в Eden), плюс происходит **автоунбоксинг** `ii` (распаковка `Integer` → `int`) для операции сложения-конкатенации.
- Результирующая строка — новый объект `String` в куче.
- `System.out` — статическое поле класса `System`, ссылающееся на объект `PrintStream`; вызывается его метод `println`, который в конце концов делает системный вызов на вывод в консоль (через нативный код, JNI).
- После выполнения строки фрейм метода `printAll` завершает свою работу, **выталкивается (pop) из стека**, вся его таблица локальных переменных (включая `uselessVar`) уничтожается вместе с фреймом. Сами объекты в куче при этом не удаляются мгновенно — они просто теряют последнюю ссылку и становятся мусором (unreachable), кандидатами для GC.

### `System.out.println("finished");` — строка 7
- Управление возвращается в фрейм `main` (после `pop` фрейма `printAll`).
- Строковый литерал `"finished"` не создаётся заново в куче — он берётся из **пула строк (String Pool / intern pool)**, который живёт в куче, но управляется особым образом: JVM при первой встрече такого литерала кладёт его туда один раз, и повторное использование того же литерала возвращает ту же ссылку.
- Вызывается `println`, строка выводится в консоль.
- После этого метод `main` завершается, его фрейм выталкивается из стека, стек потока `main` пустеет, поток завершается, JVM (если это был единственный непользовательский поток) завершает работу.

## Про сборщик мусора (GC)

За время выполнения этого кода в куче накапливается несколько объектов:
- `new Object()` (`o`) — живёт до конца `main`, пока есть ссылка `o` во фрейме.
- Закэшированный `Integer(2)` — не собирается никогда, пока жив classloader `Integer` (по сути, живёт всю программу).
- `Integer(700)` (`uselessVar`) — становится мусором сразу после возврата из `printAll`.
- Промежуточный `StringBuilder` и результирующая `String` (строка 6) — становятся мусором сразу после `println`, так как ссылок на них больше нигде не остаётся.

Все эти недолгоживущие объекты создаются в **Eden**-области Young Generation. GC (например, **Minor GC** для Young Generation) сработает, когда Eden заполнится — тогда все живые (reachable) объекты будут скопированы в Survivor-область (алгоритм copying/mark-copy), а мусор (как `uselessVar` и временный `StringBuilder`/`String`) просто останется на месте и будет "стёрт" при переиспользовании Eden — то есть память под них фактически не освобождается явно, а помечается свободной для новых аллокаций. Конкретный алгоритм и момент запуска зависит от выбранного сборщика мусора (G1, Parallel, ZGC и т.д.), но принцип reachability (достижимость от GC-корней — стека, статических полей) один и тот же везде.
